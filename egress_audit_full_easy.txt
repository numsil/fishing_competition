HUK 낚시 대회 앱 — 데이터 사용량 점검 (쉬운 풀이) [통합본]
범위: 전체 (이미지, 데이터베이스, 캐시, 자동 새로고침, 로그인 등)
배포 전 정리 목적
==============================================================================

[ 다시, 'Egress'가 뭔가요? ]

서버에서 앱으로 "내려보내는 데이터의 양"입니다.
Supabase는 이 양에 따라 돈을 받습니다 — 핸드폰 데이터 요금처럼요.

종류는 4가지:
  1. Database Egress  — 게시물·댓글·점수 같은 글자 데이터
  2. Storage Egress   — 이미지·동영상 파일
  3. Realtime Egress  — 실시간 구독 데이터 (채팅 등)
  4. Cached Egress    — 캐시 적중 후 새로 받은 양

이번 점검은 4가지 모두 + 상태관리/자동새로고침/로그인 부수효과까지 봤습니다.

==============================================================================
가장 중요한 5가지 (비유로)
==============================================================================

────────────────────────────────────────────────────────────────────────────
[1] 피드 = "도서관 책 다 빌려옴"  ← 이미 해결 ✅
────────────────────────────────────────────────────────────────────────────
지금까지의 모든 게시물을 한 번에 받던 구조 → 20개씩 받기로 변경.
인스타그램·트위터처럼 스크롤 시 자동으로 더 받는 방식.
* 작업 완료. 친구들 테스트로 확인 후 발견되는 이슈 잡으면 됩니다.

────────────────────────────────────────────────────────────────────────────
[2] 이미지 = "지갑 사진 보려고 4K 포스터 다운로드"
────────────────────────────────────────────────────────────────────────────
지금 일어나는 일:
  업로드된 이미지를 1080픽셀(꽤 큼)로 저장한 다음, 어디서든 그 원본을 받음.
  - 작은 동그란 아바타(50픽셀)도 1080픽셀 다운로드
  - 피드 카드(폰 화면 폭 정도)도 1080픽셀 다운로드
  - 상세 화면도 1080픽셀 (이건 적정)

비유:
  명함에 들어갈 작은 얼굴 사진을 보고 싶은데, 전신 4K 포스터를 매번
  배송받는 상황.

영향:
  피드 한 번 스크롤(20개) ≈ 4MB 다운로드.
  사이즈 맞게 받으면 ≈ 1MB. **약 75% 절감**.

해결:
  Supabase Storage URL에 "?width=400" 같은 옵션을 붙이면 서버가 알아서
  작게 만들어 보내줌. 위젯 사용처 약 16곳에 같은 헬퍼 함수 적용.

조건:
  Supabase 프로젝트가 이 기능을 켤 수 있어야 함 (Pro 플랜 이상).
  무료 플랜이면 업로드 시 "큰 사진 + 작은 사진" 두 개 저장하는 우회로.

────────────────────────────────────────────────────────────────────────────
[3] 시즌 랭킹 = "1등 한 명 보려고 전 국민 점수표 받음"
────────────────────────────────────────────────────────────────────────────
지금 일어나는 일:
  랭킹 탭 = 모든 사용자의 모든 점수 기록 다운로드 → 폰에서 더해서 1~10등 추출.
  화면엔 10명만 보이는데도요.

해결:
  서버에 "Top 10만 계산해서 줘" 라는 함수(SQL)를 만들면 끝.
  앱은 10명분만 받음.

────────────────────────────────────────────────────────────────────────────
[4] 프로필 통계 = "내 우승 횟수 보려고 같이 참가했던 사람들 다 받음"
────────────────────────────────────────────────────────────────────────────
지금 일어나는 일:
  내 프로필의 "참가 5회 / 우승 1회" 표시 위해, 내가 참가했던 모든 리그의
  모든 참가자 + 모든 게시물을 받아 폰에서 우승 판정.

비유:
  "내가 작년에 1등 몇 번 했지?" 답을 찾기 위해 모든 대회의 모든 참가자
  성적표를 인쇄해 가져와 직접 비교.

해결:
  서버에 우승 판정 SQL 함수 추가 → 결과만 받음 (1줄).

────────────────────────────────────────────────────────────────────────────
[5] 자동 새로고침 = "잠깐 다른 앱 보고 와도 무거운 작업 자동 시작"
────────────────────────────────────────────────────────────────────────────
지금 일어나는 일:
  리그 상세 화면에서 다른 앱(메시지 등) 잠깐 보고 돌아오면, 자동으로 4가지
  데이터를 다시 받음. 그중 랭킹은 [3]번에서 본 무거운 작업.

비유:
  도서관에서 잠깐 화장실 갔다 왔더니 사서가 책을 처음부터 다시 다 가져와
  "여기서 다시 시작하세요" 하는 상황.

해결:
  - 5분 이내 재진입은 그냥 두기
  - 무거운 랭킹은 사용자가 랭킹 탭 누를 때만 갱신

==============================================================================
숨어 있던 문제 4가지 (덜 눈에 띄지만 중요)
==============================================================================

(6) 로그인 토큰 자동 갱신 → 통계 자동 재계산
    1시간마다 토큰이 갱신되는데, 그때마다 프로필/마이리그 통계가 다시 돌아감.
    사용자가 안 보고 있어도. 코드 한 줄 수정으로 해결.

(7) 화면 벗어났다 다시 들어오면 → 처음부터 다시 받기
    캐시 시간(keepAlive) 설정이 일부만 되어 있음. 15개+ Provider에 추가만
    하면 끝. 작업량 적음.

(8) "전체 컬럼 *" 사용 3곳
    필요한 것만 받지 않고 모든 컬럼 받음. 한 줄 수정.

(9) "참가자 수"만 알면 되는데 모든 ID를 받음
    같은 코드베이스에 정답이 있어서 그 패턴 4곳에 복붙.

==============================================================================
이미 잘 되어 있는 것들 (칭찬)
==============================================================================
- 피드/일반 화면 캐시 적용 (5분/3분) ✓
- 이미지 업로드 시 압축 (1080픽셀, 3MB 이하) ✓
- 동영상 업로드 시 압축 ✓
- cached_network_image 광범위 사용 (재방문 시 다시 안 받음) ✓
- 검색 디바운스 (타자 칠 때 매번 호출 X) ✓
- 실시간 채널은 DM 외엔 안 씀 — 누수 없음 ✓
- 자동 새로고침은 한 곳만 — 다른 화면은 깨끗 ✓

==============================================================================
작업 그룹 분류 (어떻게 묶어서 처리할지)
==============================================================================

──── Group α: 한 줄짜리 묶음 (반나절, 위험 낮음) ────
필요한 것만 받기, 캐시 추가, 자동 새로고침 범위 축소 등.
효과: 사용자 수와 무관하게 즉시 절감. 한 번에 5건+ 해결.

──── Group β: 이미지 사이즈 ([2]번, 1일) ────
가장 큰 단일 절감.

──── Group γ: 리그 목록 페이지네이션 (반나절) ────
[1]번 같은 패턴 한 번 더.

──── Group δ: 서버 함수(SQL) 도입 (시간 비용 큼) ────
δ1: 시즌 랭킹 ([3]번, 1~2일)
δ2: 리그 랭킹 (1~2일)
δ3: 프로필 통계 ([4]번, 2~3일, 가장 복잡)

──── Group ε: 무료 플랜에서 [2]번 못할 때 대안 ────
업로드 시 "큰 사진 + 작은 사진" 두 개 저장. 1일.

==============================================================================
권장 순서 (배포 전 다 정리할 때)
==============================================================================

   1. Group α   ─ 반나절   ◀ 시작점
   2. Group β   ─ 1일      ◀ Storage 큰 폭 절감
   3. Group γ   ─ 반나절
   4. Group δ1  ─ 1~2일    ◀ SQL 첫 작성 (단순)
   5. Group δ2  ─ 1~2일
   6. Group δ3  ─ 2~3일    ◀ 가장 복잡
   (7. Group ε  ─ Supabase 플랜 따라)

   총: 약 6~10일 (테스트 포함)

==============================================================================
시작 전 확인 한 가지
==============================================================================
Supabase 대시보드 → Settings → Storage 에서
"Image Transformation" 사용 가능한지 확인.
가능하면 [2]번을 그대로 진행, 불가하면 Group ε(우회)로 진행.

(보통 Pro 플랜 이상에서 사용 가능. 무료 플랜은 제한될 수 있음.)

==============================================================================
정리: 핵심 메시지
==============================================================================

지금 코드는 "사용자 적을 때는 멀쩡하지만, 늘면 빠르게 비싸지는" 구조.
배포 전에 다 정리하면, 사용자 수가 늘어도 비용이 천천히 늡니다.

가장 효과 큰 두 가지:
  1. 이미지 사이즈 변환 (Storage 75%↓)
  2. 서버 함수 도입 (Database 큰 폭 ↓)

가장 빠른 효과:
  Group α (반나절에 5+ 건 해결)
