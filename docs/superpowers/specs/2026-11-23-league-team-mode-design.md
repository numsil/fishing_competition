## 개정 이력

**v1 (구현 완료)** — 팀전 옵션, 팀 CRUD, 호스트 배정, 자동 셔플, 팀/개인 순위 탭.

**v2 (이 문서)** — 배정 주체와 규모 대응을 추가한다. 이유는 둘이다.

1. **배정 주체.** v1이 "호스트 배정만"을 택한 것은 기획 판단이 아니라
   `league_participants` 의 UPDATE RLS 정책이 호스트 전용이어서 생긴 결과였다.
   참가자가 직접 팀을 고르는 쪽이 자연스러운 리그도 있다.
2. **규모.** v1의 배정 UI는 1명당 2탭이다. 100명·20팀이면 200탭이 되고,
   팀 선택 바텀시트도 20줄을 스크롤해야 한다.
   실제 운영 최대 리그는 아직 12명이지만, 규모를 미리 감당해 두기로 결정했다.

v2가 바꾸지 않는 것: **1장의 핵심 설계 원칙 4개 전부, 점수 집계 규칙(3장) 전부,
`posts` 테이블, `get_league_ranking`.** v2는 "누가 `team_id` 를 쓰는가"와
"어떤 UI로 쓰는가"만 바꾼다.

## 1. 배경 / 목표

현재 리그는 전원 개인전이다. 모임·동출·동아리처럼 **편을 나눠 겨루고 싶은 수요**가 있으나,
어떤 맥락(지역 모임 / 친구끼리 / 큰 대회)에서 주로 쓰일지 아직 확정되지 않았다.

→ 따라서 팀전을 **별도 리그 타입으로 분리하지 않고, 호스트가 켜고 끌 수 있는 리그 옵션**으로 만든다.
팀전을 끈 리그는 지금과 100% 동일하게 동작한다.

### 핵심 설계 원칙

1. **각자는 평소처럼 개인전을 뛴다. 그 개인 점수를 팀 단위로 묶어 합산하는 것이 팀 점수다.**
   별도의 팀 집계 규칙을 새로 만들지 않는다.
2. **`posts` 테이블은 건드리지 않는다.** 조과에 팀 정보를 붙이지 않는다.
   팀 소속은 사람(`league_participants`)에만 존재하고, 조과는 항상 사람을 따라간다.
   → 진행 중 팀 이동이 자유롭고, 과거 조과 재계산이 필요 없다.
3. **개인 순위는 그대로 유지한다.** 팀 순위는 그 위에 얹는 레이어다.
4. **점수 계산 로직은 하나도 바꾸지 않는다.** 기존 `get_league_ranking` 을 그대로 쓰고,
   그 결과를 팀으로 묶어 보여주는 것이 팀 순위다. 집계용 신규 쿼리를 만들지 않는다.

### v2가 더하는 원칙

5. **`team_id` 를 쓰는 경로는 전부 RPC 하나를 지난다.** 참가자용(`set_my_league_team`)과
   호스트용(`assign_league_teams`) 두 개뿐이고, 정원·소속·권한 검증이 그 안에 있다.
   RLS를 완화해 참가자에게 자기 행 UPDATE를 열어주지 **않는다** (근거: 2.5).
6. **참가자 자율 선택은 호스트 권한을 빼앗지 않는다.** 참가자 권한을 *더하는* 것이다.
   자율 모드에서도 호스트는 계속 배정·셔플할 수 있다 (쏠렸을 때 뒤집을 수단이 필요하다).

## 2. 데이터 구조

### 2.1 신규 테이블: `league_teams`

| 컬럼 | 타입 | 비고 |
|---|---|---|
| `id` | uuid PK | `gen_random_uuid()` |
| `league_id` | uuid NOT NULL | → `leagues(id)` **ON DELETE CASCADE** |
| `name` | text NOT NULL | 팀명 |
| `color` | text | 팀 색상 토큰 키 (이미지 업로드 없음) |
| `sort_order` | int NOT NULL DEFAULT 0 | 표시 순서 |
| `created_at` | timestamptz DEFAULT now() | |

- `UNIQUE (league_id, name)` — 같은 리그 내 팀명 중복 금지
- CASCADE 이유: 팀은 리그 종속 메타데이터이며 조과를 담지 않는다.
  (조과 보호는 `posts.league_id` 의 **RESTRICT** 로 이미 보장됨 — `20261117090000_league_cancel_instead_of_delete.sql`)

> **v2에서 `league_teams` 에 컬럼을 더하지 않는다.** 정원은 팀별이 아니라 리그 단위다 (2.3).

### 2.2 기존 테이블 변경 (v1)

**`league_participants`**
- `team_id uuid NULL` → `league_teams(id)` **ON DELETE SET NULL**
  팀을 삭제하면 멤버는 "미배정" 상태로 돌아가고 조과는 그대로 남는다.

**`leagues`**
- `is_team_mode boolean NOT NULL DEFAULT false`

**`posts`** — 변경 없음.
**기존 RPC / 점수 로직** — 변경 없음.

> 팀 전용 집계 설정(`team_catch_limit` 등)은 **두지 않는다.** 기존 `rule` / `catch_limit` 이 그대로 적용된다.

### 2.3 신규 컬럼 (v2)

**`leagues`** 에 두 개를 더한다.

| 컬럼 | 타입 | 기본값 | 비고 |
|---|---|---|---|
| `team_assign_mode` | text NOT NULL | `'host'` | `CHECK (team_assign_mode IN ('host','self'))` |
| `team_capacity` | int NOT NULL | `0` | 팀당 정원. **0 = 무제한.** `CHECK (team_capacity >= 0)` |

기본값이 `'host'` / `0` 이므로 **기존 리그와 신규 일반 리그는 v1과 동일하게 동작한다.**

**정원을 리그 단위로 두는 이유.** 팀별 정원을 다르게 줄 실사용 근거가 없고,
팀 단위로 두면 "정원 마감" 판정이 팀마다 달라져 UI 분기와 RPC 검증이 모두 두 배가 된다.
20팀을 모두 5명으로 맞추는 것이 현실적인 용례다. 필요해지면 그때
`league_teams.capacity` 를 더해 리그 값을 기본값으로 쓰는 식으로 확장한다.

**정원이 적용되는 범위 — 호스트도 예외가 없다.**
호스트 전용 우회를 두면 "자리 없음" 판정이 두 갈래가 되고, 다중 선택 UI의 비활성 로직도
두 벌이 된다. 대신 호스트는 **정원 자체를 언제든 올릴 수 있으므로** 막히는 상황이 없다.

**정원을 현재 인원보다 작게 줄이면** 이미 초과한 팀의 멤버를 강제로 빼지 않는다.
그 팀은 "6 / 5" 로 표시되고 **새로 들어오는 것만 막힌다.** 호스트가 손으로 정리한다.

### 2.4 인덱스

- `league_teams(league_id)` (v1)
- `league_participants(team_id)` (부분 인덱스: `WHERE team_id IS NOT NULL`) (v1)
- v2는 인덱스를 더하지 않는다. 정원 계산은 `league_participants(league_id)` 로 끝난다.

### 2.5 왜 RLS를 완화하지 않는가 (v2 핵심 보안 근거)

참가자가 자기 팀을 고르게 하려면 "본인 행 UPDATE 허용"이 가장 짧은 길처럼 보인다.
**쓰면 안 된다.**

`league_participants` 는 `status` 컬럼으로 **리그 참가 승인**을 관리한다
(`'pending'` → 호스트 승인 → `'approved'`). Postgres RLS는 **컬럼 단위 제한이 불가능**하고
`WITH CHECK` 은 NEW 행만 보기 때문에, 본인 행 UPDATE를 열면 참가자가
`status` 를 `'pending'` → `'approved'` 로 바꿔 **승인을 스스로 통과**할 수 있다.

따라서 v2는 **UPDATE 정책을 건드리지 않는다.** 현재 정책 그대로 유지한다:

```
League hosts can update participants. (UPDATE)
  USING: EXISTS (SELECT 1 FROM leagues WHERE id = league_id AND host_id = auth.uid())
```

참가자의 팀 변경은 `team_id` 한 컬럼만 쓰는 `SECURITY DEFINER` RPC로만 가능하다 (3.7).
이 방식은 기존 `shuffle_league_teams` / `is_league_host` 와 같은 패턴이다.

### 2.6 FK / 스키마 변경 후 필수 검증

과거 FK 추가로 **PGRST201 embed ambiguity 장애**가 발생한 이력이 있다.
마이그레이션 적용 직후 아래를 반드시 확인한다.

- `league_participants` → `users` FK가 여전히 1개뿐인지 (`pg_constraint` 확인)
- PostgREST embed 실제 호출 200 확인 (**코드의 select 문자열을 그대로 복사해서** 호출):
  - `league_participants?select=id,users(username,avatar_url)`
  - `league_participants?select=user_id,team_id`
  - `league_teams?select=id,name,color,sort_order,league_participants(user_id)`
  - `leagues?select=id,status,is_team_mode,team_assign_mode,team_capacity`
  - `posts?select=id,users(username,avatar_url)`

v2는 FK를 추가하지 않으므로 embed 모호성 위험은 낮지만, `leagues` select 목록에
**새 컬럼 2개가 빠지면 기능이 조용히 꺼진다** (v1에서 `is_team_mode` 를 5곳에
넣어야 했던 것과 같은 함정). 아래 전부를 확인한다.

- `league_repository.dart` — `getLeague` / `getLeagues` / `getMyJoinedLeagues`
- `my_league_repository.dart` — 2곳

## 3. 점수 집계 규칙

> **v2는 이 장을 전혀 바꾸지 않는다.** 배정 주체가 바뀌어도 점수 계산은 동일하다.

### 3.1 기본 규칙

**팀 점수 = 그 팀 멤버들의 개인 점수 합계.**

각 멤버의 개인 점수는 **기존 개인 순위와 완전히 동일하게** 계산된다 —
즉 리그의 `rule` 과 `catch_limit` 이 각 **개인에게** 적용되고, 그 결과를 팀별로 더한다.

새로운 집계 규칙도, 새로운 호스트 설정도 없다.

| 리그 설정 | 팀 점수 |
|---|---|
| `최대어` (1마리) | 팀원 **각자의 최대어 1마리**를 모두 더한 값 |
| `합산 길이`, `catch_limit = 3` | 팀원 **각자의 상위 3마리 합**을 모두 더한 값 |
| `합산 길이`, `catch_limit = 0`(전체) | 팀원 각자의 전조과 합을 모두 더한 값 |
| `무게` | 위와 동일, 단위만 g |
| `마릿수` | 팀원 각자의 마릿수를 모두 더한 값 |

### 3.2 계산 예시 (5명 팀)

| 멤버 | 조과(cm) | `최대어`(1마리) | `합산 길이` 3마리 |
|---|---|---|---|
| 갑 | 92, 61, 50, 48 | 92 | 92+61+50 = 203 |
| 을 | 86 | 86 | 86 |
| 병 | 70, 68 | 70 | 70+68 = 138 |
| 정 | 55 | 55 | 55 |
| 무 | — | 0 | 0 |
| **팀 합계** | | **303** | **482** |

멤버 줄에 표시하는 "기여 점수"는 **개인 순위표에 나오는 그 사람의 점수 그대로**다.
별도 계산이 없으므로 개인 탭과 팀 탭의 숫자가 어긋날 수 없다.

### 3.3 인원 불균형

이 방식은 **인원이 많은 팀이 유리하다.** 평균·가중치 보정은 **넣지 않는다.**
호스트가 인원을 맞춰 팀을 짜는 것을 전제하고, `자동 셔플` 이 균등 분배한다.
(평균 점수 표시도 하지 않는다.)

v2의 **팀 정원**이 이 불균형을 구조적으로 막는 1차 수단이 된다 — 특히 자율 선택 모드에서.

### 3.4 동점 처리

1. 팀 내 **최대어가 큰** 팀 우선
2. 그래도 같으면 **조과 수가 적은** 팀 우선

### 3.5 집계를 어디서 하는가 — 신규 집계 RPC 없음

순위 화면은 **이미 `get_league_ranking` 으로 개인 순위 전체를 받아온다.**
팀 점수는 그 행들을 `team_id` 로 묶어 더한 값이므로, **집계용 쿼리를 새로 만들지 않는다.**

- `get_league_ranking` — **무수정**. 그대로 재사용한다.
- 팀 명단은 가벼운 조회 **1회**로 가져온다. 멤버가 0명인 팀도 나와야 하므로
  `league_teams` 를 기준으로 조회하고 참가자를 embed 한다:
  `league_teams?select=id,name,color,sort_order,league_participants(user_id)&league_id=eq.<id>&order=sort_order`
  (순위에 없는 user_id = 미승인·탈퇴자는 화면에서 무시한다)
- 화면(Provider)에서 `user_id` 기준으로 두 결과를 합치고 팀별로 합산한다.
  - `rule = '마릿수'` → `total_count` 합
  - 그 외 → `total_length` 합 (무게 룰도 이 컬럼에 실린다)
  - 정렬: 팀 점수 DESC → 팀 내 최대어 DESC → 조과 수 ASC (3.4)

**CLAUDE.md "집계는 RPC로, 클라 fold/reduce 금지" 와의 관계**

이 규칙은 **egress 규칙**이다 — 집계하려고 원본 데이터를 끌어오는 것을 막는 것이다.
여기서는 개인 탭 표시를 위해 **이미 받아둔** 집계 결과(참가자 20~30행)를 더하는 것뿐이므로
추가 egress가 없다. 오히려 RPC를 새로 만들면 같은 데이터를 두 번 받게 된다.
→ 집계 쿼리 추가 0회, 조회 추가 1회(팀 명단)로 끝낸다.

> 참가자가 수백 명 규모로 커지면 그때 `get_league_team_ranking` RPC로 옮긴다.
> 그 시점에도 RPC는 `get_league_ranking` 을 호출해 재사용하면 되므로 전환 비용이 낮다.

### 3.6 `shuffle_league_teams(p_league_id uuid)` — v2에서 반환값 추가

v1 현재 상태: 호스트/admin 전용 `SECURITY DEFINER`, 승인된 참가자만 대상,
팀에 라운드로빈 균등 분배, 팀이 0개면 `NO_TEAMS`, **`RETURNS void`**.

v2 변경:

- **`RETURNS jsonb`** — 셔플 **직전**의 배정 스냅샷을 돌려준다:
  `[{"user_id":"…","team_id":"…"}, …]` (미배정이면 `team_id: null`)
  클라이언트가 이 값을 들고 있다가 `되돌리기` 에서 `assign_league_teams` 로 그대로 되돌린다.
- **정원 검증 추가**: `team_capacity > 0` 이고
  `승인 참가자 수 > 팀 수 × team_capacity` 면 `CAPACITY_TOO_SMALL` 예외.
  (라운드로빈은 균등 분배이므로 이 조건만 통과하면 어떤 팀도 정원을 넘지 않는다)

> **마이그레이션 주의**: 반환 타입이 바뀌므로 `CREATE OR REPLACE` 가 불가능하다.
> `DROP FUNCTION public.shuffle_league_teams(uuid);` 후 재생성해야 한다.

**되돌리기를 DB에 저장하지 않는 이유.** 스냅샷은 화면 state에만 둔다.
화면을 나가면 사라지고, 커버하는 범위는 "방금 셔플이 실수였다" 하나다.
이력 테이블을 만들면 보관 기간·권한·정리 정책이 따라붙는데 그만한 가치가 없다.

### 3.7 신규 RPC (v2) — `team_id` 를 쓰는 유일한 두 경로

**(a) `set_my_league_team(p_league_id uuid, p_team_id uuid) RETURNS void`**
참가자 본인용. `SECURITY DEFINER`, `SET search_path TO 'public'`.

검증 순서와 예외:

| 순서 | 조건 | 실패 시 |
|---|---|---|
| 1 | `auth.uid() IS NOT NULL` | `AUTH_REQUIRED` |
| 2 | 리그 존재 | `LEAGUE_NOT_FOUND` |
| 3 | `is_team_mode = true` AND `team_assign_mode = 'self'` | `SELF_PICK_DISABLED` |
| 4 | 호출자가 그 리그의 `status='approved'` 참가자 | `NOT_PARTICIPANT` |
| 5 | `p_team_id IS NULL` 이면 → 미배정으로. **정원 검증 없이 통과** | — |
| 6 | `p_team_id` 가 그 리그의 팀 | `TEAM_NOT_IN_LEAGUE` |
| 7 | `team_capacity = 0` 이거나, 그 팀의 **본인 제외** 승인 멤버 수 `< team_capacity` | `TEAM_FULL` |

통과하면 **`team_id` 컬럼만** UPDATE한다. 다른 컬럼은 손대지 않는다.

- 이미 같은 팀이면 아무것도 하지 않고 성공 (멱등)
- 리그 `status` 는 검증하지 않는다 — v1의 "진행 중 팀 이동 허용" 결정을 유지한다

**(b) `assign_league_teams(p_league_id uuid, p_assignments jsonb) RETURNS void`**
호스트용 일괄 배정. `SECURITY DEFINER`, `SET search_path TO 'public'`.
`p_assignments` = `[{"user_id":"…","team_id":"…"|null}, …]`

| 순서 | 조건 | 실패 시 |
|---|---|---|
| 1 | `auth.uid() IS NOT NULL` | `AUTH_REQUIRED` |
| 2 | 리그 존재 | `LEAGUE_NOT_FOUND` |
| 3 | `is_league_host(p_league_id)` | `NOT_LEAGUE_HOST` |
| 4 | 모든 `user_id` 가 그 리그의 `status='approved'` 참가자 | `NOT_PARTICIPANT` |
| 5 | 모든 non-null `team_id` 가 그 리그의 팀 | `TEAM_NOT_IN_LEAGUE` |
| 6 | **적용 후 상태**에서 어떤 팀도 `team_capacity` 초과 안 함 (`team_capacity > 0` 일 때) | `TEAM_FULL` |

6번이 "적용 후 상태" 기준인 것이 중요하다. 한 번에 3명을 넣는 요청이 개별로는
각각 정원 안이어도 합치면 넘을 수 있다. 또한 **이미 초과한 팀**(정원을 낮춘 경우)에서
사람이 **빠지는** 배정은 허용해야 하므로, 판정은 "초과 팀이 더 나빠지지 않는가"다.

**정확한 위반 조건**: 적용 후 인원이 `team_capacity` 를 넘고 **AND 적용 전보다 늘었다.**

"늘지 않았으면 통과"이고 "줄었으면 통과"가 아니다 — 이 차이가 실제 버그였다.
정원을 낮추면 여러 팀이 동시에 초과 상태가 되는데, 한 팀에서 사람을 빼는 배정에서
**손대지 않아 적용 전 = 적용 후인 다른 초과 팀**이 "줄지 않았다"에 걸려 `TEAM_FULL` 로
거부된다. 그러면 호스트가 초과 상태를 복구할 수단이 없어진다. (prod 실측으로 확인)

Dart 쪽 거울은 `lib/features/league/data/team_capacity.dart` 의
`assignmentsFitCapacity` 이고, 이 규칙을 그대로 구현한다. 한쪽만 고치면 UI 가 허용한
조작이 서버에서 거부된다.

이 함수 하나가 세 가지 UI를 모두 처리한다:

- 팀원 다중 추가 (4.2) — 체크한 N명을 한 번에
- 셔플 되돌리기 (3.6) — 스냅샷 전체를 한 번에
- 단건 이동 — 1개 원소 배열

> v1은 단건 이동을 `league_participants` 직접 UPDATE로 했다.
> v2는 이것도 이 RPC로 통일한다. 정원 검증이 한 곳에만 있어야 하기 때문이다.

### 3.8 팀 CRUD

v1 그대로. **호스트 전용 RLS 정책**으로 처리하며 RPC를 만들지 않는다.

- `league_teams` INSERT/UPDATE/DELETE: 해당 리그의 `host_id = auth.uid()` 또는 admin
- 호스트·admin 판별은 `is_league_host(uuid)` SECURITY DEFINER 헬퍼로 공유한다
- `league_participants` UPDATE 정책은 **호스트 전용 그대로 유지** (2.5)

> v1 설계에는 "호스트 외의 `team_id` 변경을 거부하는 BEFORE UPDATE 트리거"가 있었으나,
> 구현 시 UPDATE 정책이 이미 호스트 전용임을 확인하여 **트리거를 만들지 않았다.**
> v2도 트리거를 만들지 않는다 — 참가자 경로가 RPC뿐이므로 막을 대상이 없다.

## 4. 화면 구성

### 4.1 리그 개설 / 수정 — 목업 ⑥

`팀전으로 진행` 토글(`is_team_mode`) 아래에 **중첩된** 두 설정을 둔다.
토글이 꺼져 있으면 이 블록 전체가 보이지 않는다.

- **팀 선택 방식** — 2지 세그먼트. 기본 `호스트가 배정`
  - `호스트가 배정` → "호스트만 팀을 바꿀 수 있습니다. 자동 셔플로 한 번에 배정할 수 있습니다."
  - `참가자가 선택` → "참가자가 직접 팀을 고릅니다. 호스트도 계속 배정할 수 있습니다."
  - 선택에 따라 안내 문구가 바뀐다 (어느 쪽을 골랐는지 문구로 확인 가능해야 한다)
- **팀당 정원** — 스테퍼. `0` 이면 `무제한` 으로 표시
  - 보조 문구: "0이면 무제한"
  - **컬럼 기본값과 화면 초기값이 다르다.** `leagues.team_capacity` 의 DB DEFAULT는
    `0`(무제한) 이다 — 기존 리그와 일반 리그가 v1과 동일하게 동작해야 하기 때문이다.
    반면 개설 화면에서 `팀전으로 진행` 을 **처음 켜는 순간** 스테퍼 초기값을 `5` 로 둔다
    (팀전을 켜는 사람은 정원을 원할 가능성이 높다). 토글을 껐다 다시 켜면 직전 값을 유지한다.
    수정 모드에서는 항상 DB에 저장된 값을 그대로 보여준다.

**팀 생성은 개설 플로우에 넣지 않는다.** 개설 직후 관리 화면에서 만든다 (v1 유지).

**수정 모드**에서 두 값 모두 변경 가능. 변경이 기존 배정을 되돌리지 않는다
(`self` → `host` 로 바꿔도 이미 고른 팀은 유지).

### 4.2 리그 관리 (호스트) — `팀 관리` — 목업 ①②③

v1과 동일하게 **별도 화면(`/league/teams/:leagueId`)** 이고 관리 화면에는 진입 버튼만 둔다
(팀전 리그에서만 노출). v2는 이 화면의 **밀도와 일괄 조작**을 바꾼다.

**(1) 요약 바** — 상단 고정
`참가자 N명 · M팀` / `미배정 K명` (K>0이면 경고색, K=0이면 포인트색).
그 오른쪽에 `되돌리기`(직전 셔플이 있을 때만) + `자동 셔플` 버튼.

**(2) 팀 카드는 기본 접힘** ← v2의 핵심 변경
접힌 카드 한 줄: 색 점 · 팀명 · `사용/정원` · 펼치기 아이콘.
20팀이어도 화면에 요약이 들어온다.

- 정원이 `0`(무제한)이면 `N명` 으로 표시
- 현재 인원이 정원을 넘으면 (`6 / 5`) 경고색으로 표시
- 펼치면 멤버 줄 + 하단에 `팀원 추가 · N자리 남음` 버튼

> v1은 카드가 항상 펼쳐져 있었다. 3팀에서는 그게 맞지만 20팀에서는 성립하지 않는다.
> **팀 순위 탭(4.3)의 기본 펼침 규칙은 바꾸지 않는다** — 그쪽은 점수를 보는 화면이고
> 여기는 배정하는 화면이다.

**(3) 미배정 블록** — 팀 카드들 위에, 경고색 카드로 모아 표시 (v1 유지).
각 줄 탭 → 팀 선택 바텀시트.

**(4) 팀원 다중 추가** ← v2의 핵심 변경 — 목업 ②
팀 카드의 `팀원 추가` → 바텀시트:

- 헤더: `● <팀명>에 추가` + `N자리 남음`
- **검색 입력** — 이름으로 필터. 검색하면 **다른 팀 소속도 결과에 나온다**
  (고르면 그 팀에서 옮겨진다. 줄에 현재 소속을 표시한다)
- `미배정 N명` 라벨 + `전체 선택`
- 체크박스 줄: 아바타 · 닉네임 · 조과 수
- **남은 자리를 넘는 줄은 체크박스 비활성 + `자리 없음`**
- 하단 Primary 버튼 `N명 추가` (0명이면 비활성)
- 확인 시 `assign_league_teams` **1회 호출**

이것이 200탭을 20탭으로 만드는 지점이다.

**(5) 팀 선택 바텀시트에 검색 추가** (단건 이동용, v1 시트 개편)
팀이 8개를 넘으면 스크롤만으로는 못 찾는다. 팀명 검색 입력을 추가한다.
`미배정으로` 항목은 v1 그대로 유지.

**(6) 셔플 되돌리기** — 목업 ③
`자동 셔플` 성공 시:

- 스낵바: `N명을 M팀에 다시 배정했습니다` + `되돌리기` 액션
- 스낵바가 사라진 뒤에도 요약 바의 `되돌리기` 버튼이 남는다 (화면을 나갈 때까지)
- 되돌리기 = 스냅샷으로 `assign_league_teams` 호출 → 성공 시 스냅샷 폐기

**(7) 팀당 정원 변경** — 이 화면에서도 가능해야 한다
(개설 때 정한 정원이 틀렸을 때 리그 수정 화면까지 가게 하지 않는다).

**위치: 요약 바 바로 아래, 미배정 블록 위.** `팀당 정원` 행 + 스테퍼 한 줄.
정원이 팀 카드의 `N / M` 표시와 다중 추가의 `N자리 남음` 을 모두 지배하므로,
팀 목록을 보기 전에 눈에 들어와야 한다. 화면 하단에 두면 20팀을 스크롤해야 닿는다.

### 4.3 순위 화면 — 상단 탭 `팀` / `개인`

- 팀전이 아닌 리그는 탭 자체를 노출하지 않는다 (기존 화면 그대로).
- **기본 선택 탭 = `팀`**

**팀 탭** — v1에서 바뀌는 것은 **상단 배너 하나뿐**이다.

- 팀 카드: 순위 / 팀명(색) / 팀 점수 / 인원
- **카드는 기본으로 펼쳐진 상태**로 시작한다. 접기/펼치기는 가능.
  - 예외: 팀이 **5개 이상**이면 1위 팀만 펼치고 나머지는 접은 상태로 시작
- 펼친 내용: **멤버당 한 줄** (닉네임, 개인 점수, 마릿수)
  - 점수가 있는 멤버는 진하게, 0점 멤버는 흐리게
- 멤버 줄 탭 → **기존 `league_participant_detail_screen.dart` 재사용**
- 미배정 참가자는 하단 "미배정" 그룹으로 표시 (팀 점수 미반영)

```
🥇 A팀            482.0cm   5명
   갑             203.0cm  (4)   >
   병             138.0cm  (2)   >
   을              86.0cm  (1)   >
   정              55.0cm  (1)   >
   무               0.0cm  (0)
```

**조과 깊이 유지**: 카드 기본 펼침 덕분에 "리스트 → 멤버 탭 → 조과" **2탭**으로
기존 개인 순위와 동일한 깊이를 유지한다.

**(v2) 내 팀 배너** — 목업 ④
`team_assign_mode = 'self'` 이고 **본인이 그 리그의 승인 참가자**일 때만, 팀 카드 위에 1개.

| 내 상태 | 배너 |
|---|---|
| 미배정 | 포인트색 카드. `아직 팀을 선택하지 않았습니다` + "팀에 들어가야 내 조과가 팀 점수에 반영됩니다. 리그 중에도 바꿀 수 있습니다." + Primary 버튼 `내 팀 선택` |
| 배정됨 | 한 줄. `내 팀: ● <팀명>` + 우측 `변경` |

- `team_assign_mode = 'host'` 면 배너를 **아예 그리지 않는다** (문구도 버튼도 없음)
- 참가자가 아니거나(관전) 미승인이면 그리지 않는다
- 하단 `조과 사진 등록` 버튼은 v1 그대로 유지 (팀 탭·개인 탭 모두)

**개인 탭** — v1 그대로. 각 줄에 팀 배지(색 점 + 팀명).

### 4.4 조과 등록

**변경 없음.** 팀 정보는 사람에 붙어 있으므로 등록 시 아무것도 묻지 않는다.

### 4.5 내 팀 선택 (참가자) — 목업 ⑤ — v2 신규 화면

경로 `/league/my-team/:leagueId`. 4.3 배너에서만 진입한다.

- 상단 안내: "고르면 바로 반영됩니다. 리그 중에도 바꿀 수 있고, 등록한 조과는 따라옵니다."
- **팀명 검색 입력**
- 팀 줄 (각 줄이 탭 가능한 버튼):
  - 색 점(12px) · 팀명 · `사용/정원` 과 상태 문구 · 멤버 아바타 최대 3개 + `+N`
  - **현재 내 팀**: 포인트색 테두리 + 체크 아이콘 + `현재 내 팀 · N / M`
  - **정원 마감**: 흐리게 + 자물쇠 아이콘 + `M / M · 정원 마감`, 탭 불가
  - **빈 팀**: `0 / M · 아직 비어 있음`
- 하단: `팀에서 나가기` (Outline) + "나가면 미배정이 되고 내 조과는 팀 점수에서 빠집니다"
  - 이미 미배정이면 이 버튼을 숨긴다
- 선택 즉시 `set_my_league_team` 호출 → 성공 시 이전 화면으로 돌아가고 순위를 갱신

**호스트가 이 화면에 들어오면?** 호스트도 참가자라면 똑같이 쓸 수 있다
(자기 팀을 고르는 것이고, 남을 배정하는 건 팀 관리 화면이다).

### 4.6 에러 문구 (한국어 매핑)

RPC 예외를 사용자 문구로 바꾼다. v1의 `_message(Object e)` 패턴을 따른다.

| 예외 | 문구 |
|---|---|
| `TEAM_FULL` | 방금 정원이 찼습니다. 다른 팀을 골라주세요. |
| `SELF_PICK_DISABLED` | 이 리그는 호스트가 팀을 배정합니다. |
| `NOT_PARTICIPANT` | 이 리그의 참가자가 아닙니다. |
| `NOT_LEAGUE_HOST` | 호스트만 팀을 배정할 수 있습니다. |
| `TEAM_NOT_IN_LEAGUE` | 팀 정보가 바뀌었습니다. 새로고침 해주세요. |
| `CAPACITY_TOO_SMALL` | 정원이 너무 작습니다. 팀을 늘리거나 정원을 올려주세요. |
| `NO_TEAMS` | 먼저 팀을 만들어주세요. |
| `AUTH_REQUIRED` / `LEAGUE_NOT_FOUND` | 다시 시도해주세요. |

`TEAM_FULL` 문구가 "방금"인 것은 의도적이다. UI가 꽉 찬 팀을 미리 비활성화하므로,
이 에러가 실제로 뜨는 경우는 **다른 사람이 먼저 들어간 경합**뿐이다.

## 5. 권한 / 엣지 케이스

| 상황 | 처리 |
|---|---|
| 팀 미배정 참가자 | 개인 순위엔 표시, 팀 점수 미반영. 팀 탭 하단 "미배정" 그룹 |
| 팀 삭제 | `team_id` SET NULL → 멤버 미배정. 조과는 유지 |
| 진행 중 팀 이동 | 그 사람의 개인 점수가 새 팀으로 통째로 이동 (의도된 동작) |
| 1인 팀 | 허용. 계산식 동일 |
| 팀 0개인 팀전 리그 | 팀 탭에 안내 문구 (호스트에게만 팀 생성 CTA) |

## 6. 일부러 빼는 것 (YAGNI)

- 팀 전용 집계 규칙 / 팀 상위 N 합산 방식
- 팀 순위 집계 RPC (화면에서 묶는다 — 3.5)
- 팀 평균 점수, 인원수 가중치, 핸디캡
- 팀 채팅 / 팀 전용 피드
- 팀 로고 이미지 업로드 (색상만)
- 팀 간 조과 트레이드, 팀 교체 이력 로그
- 조과당 한 줄로 나열하는 팀 상세 뷰
- **드래그 앤 드롭 배정.** 드래그는 출발점과 도착점이 같은 화면에 있어야 성립한다.
  20팀이면 손가락으로 집은 채 자동 스크롤로 통과해야 하고, 실수로 놓으면 복구 수단이 없다.
  4.2(4)의 다중 선택이 같은 문제를 더 적은 조작과 더 적은 코드로 해결한다.
- **밸런스 셔플**(실력 기준 균등 분배). "실력"의 정의(최근 몇 경기? 평균? 최대어?)와
  신규 유저 처리 규칙이 먼저 필요하고, 실제 대형 리그가 생기기 전엔 검증할 수 없다.
  현재 random 셔플 + 되돌리기로 충분하다.
- **팀별 정원**(`league_teams.capacity`). 리그 단위로 충분하다 (2.3).
- **셔플 이력 테이블.** 되돌리기는 화면 state로 충분하다 (3.6).
- **팀 선택 마감 시한 / 리그 시작 시 팀 잠금.** v1의 "진행 중 팀 이동 허용" 결정과
  충돌하고, 진행 중에 개설한 리그에서는 아무도 팀을 못 고르는 상태를 만든다.
- **자율 모드에서 호스트 배정 권한 제거.** 쏠렸을 때(9/4/2) 뒤집을 수단이 필요하다 (원칙 6).
