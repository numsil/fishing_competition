현재: imageUrl: url 만 전달 — 1080px 원본을 모든 화면에서 다운로드.

문제점: Storage Egress. Supabase Storage는 URL 쿼리 파라미터로 서버측 리사이즈 지원
       (?width=&height=&quality=&resize=). 작은 아바타도 1080px 원본을 받고 있음.
심각도: Critical
예상 영향: 피드 1회 진입(20개 게시물) ≈ 4MB → 화면 폭(400px) 맞게 받으면 ≈ 1MB.
          75% 이상 절감 가능.
수정 방향:
  - 헬퍼 함수: 원본 URL + width 파라미터 합친 URL 생성기 (core/utils 등에)
  - 위젯별 호출: avatar 80~160px, 피드 카드 800~1200px, 상세 1080px (또는 디바이스 픽셀 비율 ×)
  - memCacheWidth/Height도 함께 지정 (메모리 비용)
리스크: Storage 변환 활성화 여부 Supabase 프로젝트 설정 확인 필요.
       Pro 이상 플랜에서 image transformation 사용 가능 — 무료 플랜 제한 점검.
       무료 플랜이면 업로드 시 다중 사이즈(B-2-3)로 우회 필요.

문제점: DB Egress + 빈도. supabase_flutter의 onAuthStateChange는

  옵션 A: currentUser.id 만 watch (로그인/로그아웃 시 변경)
  옵션 B: 별도 SIGNED 이벤트만 emit하는 stream provider 작성
리스크: 로그아웃 후 즉시 dispose가 안 되면 다음 사용자에게 stale 데이터 — 단,
       main.dart의 ProviderScope 재생성으로 이미 처리됨.

------------------------------------------------------------------------------

  }

문제점: DB Egress(빈도). 잠깐 다른 앱 보고 와도 매번 4 Provider 재페치.
       leagueRanking은 A-3-10에서 무거운 쿼리. 사용자 패턴상 자주 발생.
심각도: High
예상 영향: 사용자가 리그 상세 머무는 동안 알림 확인 등으로 백그라운드 ↔ 포그라운드

수정 방향:
  - 옵션 A: 마지막 refresh 후 N분 미만이면 skip (debounce by time)
  - 옵션 B: 진행중 리그만 / 호스트 화면만 refresh
  - 옵션 C: leagueRanking 제외 — 랭킹은 사용자 탭 클릭 시 invalidate
  - 권장: A + C 조합 (5분 이내 재진입 skip + 랭킹 제외)
리스크: 진행중 리그에서 정보 stale 가능. 사용자가 직접 pull-to-refresh 가능하면 OK.
